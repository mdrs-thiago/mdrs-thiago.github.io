Da última aula

Vimos LLMs como "cérebros probabilísticos": prompt engineering, Chain-of-Thought, RAG.

Um LLM sozinho só responde. Hoje ele vai agir: consultar ferramentas, chamar APIs, tomar decisões em etapas.

O que é um Agente de IA?

Um agente combina um LLM com um loop de decisão: ele observa o estado do mundo, decide uma ação, executa, observa o resultado, e repete.

LLM comum

Prompt → Resposta. Uma única passada, sem memória de ação.

Agente

Prompt → Pensa → Age → Observa → Pensa de novo → ... → Resposta final.

Anatomia de um agente

Por trás de qualquer agente — simples ou sofisticado — estão sempre as mesmas quatro peças:

Percepção

O que o agente "vê": a pergunta do usuário, o resultado da última ferramenta, uma leitura de sensor.

Raciocínio

O LLM decidindo o próximo passo: qual ferramenta chamar, ou se já pode responder.

Ação

A ferramenta de fato executada: uma API, uma busca, uma função Python.

Memória

O que o agente "lembra" entre um passo e outro — e entre uma conversa e outra.

Arquitetura ReAct (Reason + Act)

Um dos padrões mais usados para agentes: alterna explicitamente entre raciocínio (texto livre) e ação (chamada de ferramenta).

Pergunta: Qual a temperatura em Copacabana agora, em Fahrenheit?

Thought: Preciso da temperatura atual em Copacabana. Vou usar a ferramenta de clima.
Action: buscar_clima("Copacabana, RJ")
Observation: 28°C, céu limpo

Thought: A pergunta pede Fahrenheit. Preciso converter.
Action: calcular("28 * 9/5 + 32")
Observation: 82.4

Thought: Já tenho a resposta final.
Answer: Está 82.4°F em Copacabana agora.

Além do ReAct: outros padrões de agente

Plan-and-Execute

Planeja todos os passos antes de agir, e só então executa em sequência — menos flexível, porém mais previsível e mais barato (menos idas e vindas ao LLM).

Reflexion

Depois de agir, o agente critica a própria resposta e tenta de novo se achar que errou — troca velocidade e custo por qualidade.

ReAct continua sendo o padrão mais comum porque fica no meio-termo: mais barato que Reflexion, mais flexível que Plan-and-Execute quando o problema muda no meio do caminho.

Como o LLM "sabe" quais ferramentas existem?

Não é mágica: a cada chamada, você envia junto com a pergunta uma lista de ferramentas disponíveis — nome, descrição e os parâmetros que cada uma espera.

{
  "name": "buscar_clima",
  "description": "Retorna a temperatura atual de uma cidade",
  "parameters": {
    "cidade": { "type": "string" }
  }
}
O modelo não executa nada — ele só devolve qual ferramenta chamar e com quais argumentos. Quem roda de verdade é o seu código, que devolve o resultado real pro modelo continuar.

Mas essa descrição fica onde, exatamente?

Na API, tools é um parâmetro separado de messages — não é você quem escreve isso dentro do system prompt. Mas o modelo só entende texto/tokens, não JSON estruturado. Então, por baixo dos panos, o provedor (Ollama, OpenAI, Anthropic...) serializa essa lista de ferramentas e injeta no contexto que o modelo de fato lê — tipicamente junto com as instruções de sistema, antes da sua pergunta.

O que você envia (API)

messages: [...]
tools: [...] — campos separados

O que o modelo "lê" (contexto)

Um único bloco de texto/tokens: instruções + ferramentas descritas + a conversa, tudo junto

É por isso que a descrição da ferramenta "conta" como instrução pro modelo — ela literalmente vira parte do que ele lê antes de decidir o que fazer. Uma descrição vaga é, na prática, uma instrução vaga.

Onde mora a memória de curto prazo?

Fato pouco intuitivo: o LLM não guarda nada entre uma chamada e outra. Cada chamada de API é isolada — sem sessão, sem estado no servidor do modelo.

Chamada 1: [ {user: "Oi, meu nome é Ana"} ]
Chamada 2: [ {user: "Oi, meu nome é Ana"}, {assistant: "Oi Ana!"}, {user: "Qual meu nome?"} ]
"Lembrar" de uma conversa é ilusão de interface: o seu código reenvia o histórico inteiro, de novo, a cada chamada. Se você parar de reenviar uma mensagem antiga, é como se ela nunca tivesse existido pro modelo.

Como se gerencia memória na prática?

Truncagem / janela deslizante

Descarta as mensagens mais antigas quando o histórico fica grande demais pra caber no contexto.

Sumarização

De tempos em tempos, comprime o histórico antigo num resumo curto, liberando espaço sem perder tudo.

Recuperação (RAG)

Guarda tudo fora do LLM, num banco vetorial; a cada pergunta, busca só os trechos relevantes e injeta no contexto.

Ferramentas de memória

O próprio agente ganha ferramentas como salvar_memoria()/buscar_memoria(), e decide sozinho o que vale a pena guardar.

Por que isso importa?

  • LLMs erram em contas e em fatos recentes — ferramentas externas resolvem isso
  • Separar "pensar" de "agir" torna o processo auditável: dá pra ver onde o agente errou
  • É a base de praticamente todo produto de "IA agêntica" que existe hoje

Agentes no mundo real

  • Assistentes de código: GitHub Copilot (modo agente), Claude Code — leem seu repositório, editam arquivos, rodam comandos
  • Atendimento ao cliente: agentes que consultam pedidos, emitem reembolsos, e escalam pra um humano quando necessário
  • Pesquisa: agentes que buscam em múltiplas fontes, cruzam informação e escrevem um resumo com citações

Riscos, custos e governança

  • Ações irreversíveis (enviar um e-mail, cobrar um cartão) precisam de confirmação humana antes de executar
  • Custo: cada "pensamento" é uma chamada de LLM — um agente com loops longos pode custar muito mais que uma resposta única
  • Governança: quem pode criar um agente, quais ferramentas ele pode acessar, e quem monitora se ele está funcionando bem?
Autonomia sem perder controle é exatamente o que separa um protótipo de fim de semana de um produto real.

Rodando um LLM localmente

Todo agente precisa de um "cérebro" — um LLM. Vamos rodar um na sua própria máquina, sem depender de API paga.

FerramentaComo funciona
OllamaBaixa e roda modelos abertos (Llama, Mistral, Gemma...) localmente, expõe uma API HTTP em localhost:11434
LM StudioInterface gráfica para rodar modelos locais, também expõe API compatível com OpenAI
Quest “Rodar uma LLM local”: instale o Ollama, baixe um modelo (ollama pull llama3.2) e converse com ele pelo terminal (ollama run llama3.2). Enviar comprovação →

Exemplo: chamando o LLM local via HTTP

curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2",
  "prompt": "Resuma em uma frase o que é um agente ReAct.",
  "stream": false
}'

É essa mesma chamada HTTP que dá ao seu agente a capacidade de "pensar" — na próxima aula, você vai ver ferramentas visuais fazendo exatamente essa chamada por baixo dos panos.

Limitações técnicas a ter em mente

  • Agentes podem entrar em loops (repetir a mesma ação sem convergir)
  • Ferramentas mal descritas levam a ações erradas: a descrição da ferramenta importa tanto quanto o código dela
  • Em loops muito longos, o agente pode "perder o fio da meada" mesmo dentro da janela de contexto
