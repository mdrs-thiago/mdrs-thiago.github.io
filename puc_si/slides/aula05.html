Branches, PRs e Code Review

Prof. Thiago Medeiros

Nunca commite na Main!

A Main (ou Master) é sagrada. Ela reflete o que está em Produção.

Use Branches para tudo:

  • feature/login-page
  • fix/botao-quebrado
  • experiment/nova-arquitetura

O Pull Request (PR)

É o momento da verdade. Você pede permissão para jogar seu código na Main.

Checklist de um Bom PR:

  • Título Claro: "Adiciona autenticação OAuth2" (Não use "ajustes").
  • Descrição: O que mudou? Por que?
  • Screenshots: Se mudou UI, mostre!
  • Testes: Passaram?
Code Review (O papel do colega):
Não é para ser chato. É para encontrar bugs que o autor não viu (Tunnel Vision) e garantir padrão de qualidade.

Workflow na Prática

  1. git checkout main
  2. git pull origin main (Garante que está atualizado)
  3. git checkout -b feature/minha-feature
  4. ... (Programa, Cria, Testa) ...
  5. git add .
  6. git commit -m "Implementa funcionalidade X"
  7. git push origin feature/minha-feature
  8. (Vai no GitHub e abre o PR)

Commit Semântico

Escreva mensagens para humanos, não para robôs.

Ruim ❌

  • "wip"
  • "fix"
  • "ajustes finais"
  • "agora vai"

Bom ✅ (Conventional Commits)

  • feat: adiciona login por google
  • fix: corrige erro no calculo de frete
  • docs: atualiza readme
  • chore: atualiza dependencias

Hands-on: Lab 05

Simulação de Time Ágil
  1. Dividir a turma em Squads (3-4 pessoas).
  2. Cada um cria uma Branch para uma "feature" simples (ex: criar um arquivo text com seu nome).
  3. Todos abrem Pull Requests.
  4. Troca: Membro A revisa o PR do Membro B (comentem no código!).
  5. Merge na Main apenas após aprovação.
